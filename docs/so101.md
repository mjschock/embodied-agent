# SO-101 native LeRobot reference

`SO101LeRobot` makes Hugging Face LeRobot's flagship SO-101 follower a native embodiment boundary without exposing raw joint control to a high-level agent.

## Why SO-101

SO-101 is useful here as the canonical LeRobot manipulation reference. It lets the project verify that the same embodiment/tool architecture used for simulator-specific backends also works with LeRobot's own `Robot` interface.

The adapter targets LeRobot 0.6.x; the optional dependency currently requires `lerobot[feetech]>=0.6.1,<0.7`.

```bash
pip install -e ".[so101]"
```

## Native boundary

The pinned LeRobot v0.6.1 SO follower exposes six position features:

- `shoulder_pan.pos`
- `shoulder_lift.pos`
- `elbow_flex.pos`
- `wrist_flex.pos`
- `wrist_roll.pos`
- `gripper.pos`

The first five joints use degrees when `use_degrees=true`; the gripper remains normalized to 0–100. With `use_degrees=false`, the five arm joints use LeRobot's -100–100 normalized range while the gripper remains 0–100.

`SO101LeRobot.observe()` converts those motor features into explicit state fields and places any non-motor observation features (for example configured camera frames) in `Observation.images`.

## Safety boundary

The adapter intentionally contains no direct call to native `Robot.send_action()`.

By default it advertises only `OBSERVE`. `MANIPULATE` appears only when application code injects:

1. a semantic manipulation executor; and
2. an explicit allowlist of named manipulation behaviors.

The agent-facing tool is:

```text
so101.manipulate(behavior=<named behavior>, target=<optional semantic target>, max_duration_s=<optional bound>)
```

`behavior` is intentionally distinct from the outer `manipulate` skill. The adapter rejects any behavior name not present in its configured allowlist. The executor, not the high-level agent, owns conversion from the named behavior to LeRobot policies/actions. Raw joint target fields are not part of the MCP schema.

This keeps future policy implementations free to use ACT, SmolVLA, PI-family policies, scripted skills, or another LeRobot policy while preserving one safe semantic agent boundary.

## Hardware configuration

`configs/so101.example.json` is deliberately observation-only:

```json
{
  "robots": {
    "so101": {
      "adapter": "lerobot_so101",
      "params": {
        "port": "/dev/tty.usbmodem_REPLACE_ME",
        "robot_id": "embodied-agent-so101",
        "calibrate": true,
        "disable_torque_on_disconnect": true,
        "max_relative_target": 10.0,
        "use_degrees": true
      },
      "tools": ["observe"]
    }
  }
}
```

A semantic manipulation executor is a code-level dependency and therefore cannot be enabled merely by editing this JSON file.

## CI contract

Normal unit tests inject a fake native LeRobot robot, so the base development environment stays lightweight and hardware-free. A separate `so101-lerobot-contract` workflow checks out the exact LeRobot v0.6.1 release commit (`7e241bd630a3719a56157a497ce5d08f244784f1`) and statically verifies the SO-101 config alias, six motor names, and lifecycle/observation/action method surface.

This source-contract gate detects upstream API drift without installing LeRobot's full training stack or pretending that CI is a physical-arm test.

The first implementation run also caught an API-design issue: `Embodiment.execute(skill, **params)` already reserves the keyword `skill`, so the inner manipulation selector was renamed to `behavior`. That contract is now covered on Python 3.11, 3.12, and 3.13.

## Not yet proven

- physical SO-101 connection/calibration from `embodied-agent`;
- camera configuration through the default JSON factory;
- any specific manipulation policy or task-success metric;
- sim-to-real transfer for SO-101.

Those remain later milestones. The first adapter establishes the native LeRobot compatibility and safety boundary only.
